Real-game container structure

The real dome lives inside a scaled/panned ancestor container that keeps the camera centered — this wraps the test object the same way and moves it out to world coordinates in the tens of thousands, instead of drawing directly at screen-center.

My very first in-game fix used addressMode alone, still had this redundant reassignment left over from an earlier theory, and stayed broken. Never actually isolated whether this specific pattern mattered — testing it here closes that loop.

Confirmed directly in the real game's own init call: resolution: window.devicePixelRatio || 1, autoDensity: true — neither was ever set in this test harness before now, so it's been silently using resolution:1 regardless of your actual display. preference:'webgl' is also confirmed to match Pixi's own default, so the renderer backend itself was never the difference. This toggle fully re-initializes the Pixi application, since resolution/autoDensity can only be set at init time.

Genuinely new, not another guess: the real dome's hex sprite is HALF the mask's own height (domeRadiusY, not domeRadiusY*2), anchored (0.5, 1) so its bottom edge sits at the flat base line — a full-size mask over a half-size, bottom-anchored sprite. This test harness has always used a symmetric sprite matching a symmetric mask instead. The UV math should be self-consistent regardless of absolute size, in theory — but "in theory" hasn't been reliable evidence on this specific bug so far.
