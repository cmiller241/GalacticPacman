# Asteroid Bob

The game exists in two forms built from the same design:

- **LÖVE (desktop):** `main.lua` + `lua/` + `tiled/`. Run with LÖVE 11.x from this folder (`love .`).
- **Browser:** `js/`, a JavaScript port of the Lua code, running on a small
  re-implementation of the LÖVE API (`js/love/`) drawn with WebGL2.

## Running the browser version

```
npm install        # once (installs esbuild)
npm run build      # bundles js/main.js -> dist/bundle.js
npm run serve      # static server on http://localhost:8765
```

Then open http://localhost:8765/index.html. Use `npm run watch` to rebuild on every save.

The browser can't load files synchronously the way LÖVE does, so every image
and sound is preloaded first. The list (`js/assetList.js`) is generated by
`npm run assets`, which `build` and `watch` run for you. It finds paths by
scanning `js/` for `'img/...'` and `'sounds/...'` string literals.

## How the port is laid out

- `js/love/`: the LÖVE stand-in. `graphics.js` (shapes, images, canvases,
  meshes, sprite batches, fonts, stencils, blend modes, and shaders written in
  LÖVE's GLSL dialect), `audio.js` (Web Audio), `input.js` (keyboard, mouse,
  Gamepad API), `index.js` (timer, image data, math, filesystem stubs, the
  main loop), and `lua.js` (helpers for Lua semantics: floored `%`,
  `math.random`'s three forms, `string.format`).
- Every `lua/x/Y.lua` has a matching `js/x/Y.js`, and `main.lua` maps to
  `js/main.js`. Differences from the Lua:
  - Arrays are 0-based.
  - Functions that returned several values return an array.
  - Lua tables keyed by objects are `Map`s/`Set`s.
- Tiled maps are converted with `npm run maps` (`tools/tiled-lua-to-js.mjs`),
  which turns `tiled/*.lua` into `js/levels/*.js`.
- The old PixiJS version of the game is kept in `archive/js-pixi-old/`.

Changes made in `lua/` don't carry over to `js/` on their own; each one has to
be made in both places.

## Where things are

The same layout in `lua/` and `js/`:

- `main.lua` / `js/main.js`: `love.load`, and `love.update` / `love.draw` as a
  list of named steps in the order they run. `START_AT` at the top picks where
  Bob starts, for testing.
- `setup/StartPositions`: the named start positions and the T teleport list.
- `debug/DebugDraw`: the debug overlays (C collision shapes, A belt cells,
  R gravity rings).
- `ui/Hud`: the text readout in the top-left corner.
- `entities/Player` plus `entities/player/`: the player is split by job.
  `Player` has his state, update, ball mode, teleport, death and respawn;
  `Movement`, `Rendering` and `Targeting` hold the rest of his methods and are
  copied onto `Player` when it loads. `Tuning` has the timings both use.
- `systems/WaterSystem` plus `systems/water/`: spraying, droplets, portals and
  the per-frame update are in `WaterSystem`; the parts are `Tuning` (every
  number and color), `Shared` (the state the parts share, as `shared.<name>`),
  `Oceans`, `LevelGrid`, `PlanetGrids`, `Effects`, `Obsidian`, `Ice` and
  `Rendering`.
- `world/TiledTerrain` plus `world/tiled/`: `TiledTerrain.load` puts together
  `Tiles`, `TerrainShape`, `ClimbShapes`, `Level` and `Baking`.

In those split modules, a part that adds functions to the main table
(`WaterSystem.draw`, say) defines them on its own `api` table, and the main
file copies them on, refusing duplicates.
